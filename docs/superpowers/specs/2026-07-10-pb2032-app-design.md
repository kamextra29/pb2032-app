# Spécification — Application « PB 2032 » (identification de branchements GRDF)

Date : 2026-07-10 · Statut : validé sur le principe par l'utilisateur (conception présentée et approuvée en session, avec ajout « création de branchement »)

## 1. Contexte et objectif

SLTP réalise pour GRDF des campagnes d'identification de branchements gaz (marché « Protection
Branchements 2032 »), potentiellement suivies d'une détection. Le client fournit un fichier
Excel normé (« Annexe 7 ») que les équipes doivent compléter sur le terrain puis restituer
**strictement au même format** (colonnes, couleurs, listes déroulantes, formules, onglet
récapitulatif financier intacts).

L'application remplace la saisie Excel sur le terrain : consultation et complément des fiches
branchement sur téléphone Android hors ligne, photos des coffrets, puis export du fichier
Excel conforme + ZIP de photos au bureau.

Utilisateur : conducteur de travaux / équipes terrain SLTP, non-développeurs. Interface
entièrement en français.

## 2. Périmètre

**Inclus :**
- Import du fichier client (.xlsx, onglet « Protection Branchements 2032 »).
- Consultation, recherche (scan code-barres en premier), navigation par commune/rue/n°, filtres.
- Édition des fiches : infos client (A–K, corrigibles), identification (O–V, AE–AG), report (AH–AN).
- Calcul automatique de la colonne V (Pression) en direct à l'écran.
- Ajout d'un branchement absent du fichier source.
- Photos par branchement, compressées, renommées automatiquement, exportées en ZIP.
- Export Excel « chirurgical » : fichier original modifié uniquement sur les cellules saisies.
- Réimport d'une nouvelle version du fichier client avec fusion (saisies terrain conservées).
- Fonctionnement 100 % hors ligne après installation (PWA).

**Exclus (décisions utilisateur) :**
- Colonnes L, M, N (zone « Commande GRDF ») : jamais affichées ni modifiées.
- Colonnes W à AD (section Régulateur, masquées dans le fichier) : ignorées, préservées telles quelles.
- Colonne AO (Statut branchement PB 2032) : non saisie sur le terrain, préservée telle quelle.
- Synchronisation multi-appareils : hors périmètre (le fichier est découpé en amont par équipe).
- Géolocalisation / GPS : hors périmètre (évolution future possible).
- Onglet « RCT marché Avenanté » : jamais modifié (ses formules se recalculent seules dans Excel).

## 3. Le fichier client de référence

Fichier analysé : `Annexe 7 LOT 5 SLTP BFC CR - Marché PB2032.xlsx` (4,2 Mo), version 1.3 de
l'annexe 7. Trois onglets :

| Onglet | Contenu |
|---|---|
| `RCT marché Avenanté` | Récap financier : formules `COUNTIFS`/`SUMIFS` sur le tableau terrain |
| `Protection Branchements 2032` | Tableau structuré Excel `Tableau1` (A3:AO25556), en-têtes lignes 1–3 (fusions + couleurs par zone), données à partir de la ligne 4 |
| `Listes` | Sources des listes déroulantes (colonnes A à AA) |

### 3.1 Volumétrie et données

- 25 556 lignes de tableau pré-formatées ; **931 lignes réellement remplies** (lignes 4 à 934) dans le fichier du lot 5.
- ~178 lignes ont déjà une identification partielle, 165 un type de report : l'app doit afficher et laisser modifier l'existant.
- L'adresse (commune, rue, n°) **n'est pas unique** (jusqu'à 53 branchements à la même adresse, 131 lignes sans n°). Le **PCE est unique** quand renseigné (923/931).
- **Contrainte technique majeure : la feuille principale décompressée pèse ~60 Mo** (formules V répétées sur 25 556 lignes). Tout traitement du XML doit se faire en texte ciblé (recherche/remplacement par bloc de ligne `<row>`), jamais par chargement DOM complet, et dans un Web Worker pour ne pas figer l'interface.

### 3.2 Zones de colonnes

| Zone | Colonnes | Traitement app |
|---|---|---|
| Emprise du chantier (infos client) | A–K | Affichées, **modifiables** (vérifier la donnée client fait partie de la mission) ; valeur d'origine conservée et visible |
| Commande GRDF | L, M, N | Ignorées, préservées |
| Identification PB 2032 | O–V, AE, AF, AG | Saisie terrain (V calculée) |
| Régulateur (masquée) | W–AD | Ignorées, préservées (AB contient une formule VLOOKUP, ne pas y toucher) |
| Report branchement | AH–AN | Saisie terrain |
| Statut PB 2032 | AO | Ignorée, préservée |

### 3.3 Listes déroulantes (17)

Les listes sont lues **dynamiquement** à l'import depuis l'onglet `Listes` et les plages
nommées du classeur (pas de valeurs codées en dur dans l'app), afin de suivre les évolutions
du client d'un lot à l'autre. Colonnes concernées côté saisie :

| Colonne | Liste (plage nommée) | Source |
|---|---|---|
| O Constat Coffret | `COFFRET` | Listes!A2:A5 |
| P Constat BRT CARTO | `BRT` | Listes!B2:B6 |
| Q Matière | `Matiere` | Listes!E1:J1 (PE, Ac, Cu, Pb, Solacier, Métal) |
| R Diamètre | `INDIRECT(Q)` — **cascade** | si Q=PE → 20/32/Autre ; sinon → « - » |
| S Accessoires coffret | `Equipement_coffret` | Listes!D2:D6 |
| T Bague de protection | `PROTECTION` | Listes!K2:K6 (NON, PBDI, MBDI, DPBE, DPBA) |
| AF Phase terrain | dynamique (`SORT(UNIQUE(Tableau1[Phase terrain]))`) | valeurs existantes du tableau + saisie libre |
| AG Identification PB 2032 | `VALEUR` | {1} |
| AH Type report | validation étendue x14 | Listes!R2:R5 (`TYPE_REPORT_AVENANT`) |
| AI Appareil de détection | `APPAREIL` | Listes!V2:V5 |
| AJ Classe du branchement | `BRT` | Listes!B2:B6 |
| AK Point d'arrêt | `Point_d_arret_client` | Listes!T2:T3 |
| AL Cause de la DI technique | `DI_technique` | Listes!S2:S6 |
| AM Ajout N° adresse | `VALEUR` | {1} |

Colonnes I, J, K (infos client) : saisie libre en édition (le fichier n'y impose pas de liste),
mais proposer en suggestion les valeurs déjà présentes dans la colonne.
U (longueur d'introduction de sonde si DPBE) : champ numérique, affiché seulement si T=DPBE.
AE, AN : texte libre. D (N°) : texte libre (le fichier contient 4B, 2A…).

### 3.4 Formule V (Pression) — logique à reproduire à l'identique

Entrées : S (accessoires) et T (bague). Sortie : `MPB`, `BP` ou `à renseigner`.

```
si S = "Robinet de coupure gaz, détendeur(s), compteur(s)"      → MPB
si S = "Robinet de coupure gaz, détendeur(s)"                   → MPB
si S = "Robinet de coupure gaz, compteur(s)"                    → BP
si S = "Robinet de coupure gaz seul"
   ou S = "Robinet ... déposé(és) (improductif)" :
      si T ∈ {PBDI, MBDI, DPBE, DPBA}                           → MPB
      sinon (T = NON ou vide)                                   → à renseigner
sinon (S vide ou autre)                                         → à renseigner
```

La comparaison se fait sur les **valeurs des cellules Listes!D2:D6 / K2:K6 / L2:L4 lues à
l'import** (pas sur des chaînes en dur), comme la formule originale.

Dans le fichier exporté, **V reste une formule** (inchangée) : Excel recalcule à l'ouverture.
Exception : 7 lignes du fichier ont V écrasée par une valeur en dur (`MPB`) ; si S ou T d'une
telle ligne est modifiée dans l'app, la valeur en dur est remplacée par le résultat recalculé.

## 4. Plateforme et architecture

- **PWA hors-ligne** en JavaScript sans framework (même socle que l'app VPS existante) :
  HTML/CSS/JS, service worker avec cache versionné (`CACHE = 'pb2032-vN'`), manifest.
- Hébergement : GitHub Pages, dépôt public `kamextra29/pb2032-app`, production
  `https://kamextra29.github.io/pb2032-app/`.
- **Aucune donnée client dans le dépôt** (noms, adresses, PCE = données personnelles) :
  le fichier Excel, les saisies et les photos restent exclusivement dans l'appareil
  (IndexedDB). Les fixtures de test sont synthétiques.
- Bibliothèques : JSZip (lecture/écriture du conteneur .xlsx et du ZIP photos), vendorée
  localement (pas de CDN, contrainte hors ligne). Pas d'autre dépendance d'exécution.
- Traitements lourds (import, export, compression photo) dans un **Web Worker** avec
  indicateur de progression.
- Cible : Android (Chrome) pour le terrain, Windows (Chrome/Edge) pour le bureau.
  Un seul dossier actif par appareil.

### Modules (logique testable séparée de l'interface)

| Module | Rôle |
|---|---|
| `xlsx-reader` | extraction ZIP, parsing ciblé des lignes de données, sharedStrings, plages nommées, onglet Listes |
| `xlsx-writer` | injection chirurgicale des valeurs dans le XML d'origine (texte, par bloc `<row>`), `fullCalcOnLoad` |
| `regles` | formule V, statut d'une fiche, complétude, tri intelligent des numéros |
| `fusion` | rapprochement ancien/nouveau fichier au réimport |
| `photos` | compression, nommage, ZIP d'export |
| `store` | accès IndexedDB |
| `ui/*` | écrans |

## 5. Modèle de données (IndexedDB)

- `dossier` : fichier original (Blob), nom, date d'import, métadonnées (position des lignes,
  listes extraites, valeurs de référence Listes pour la formule V).
- `branchements` : un enregistrement par ligne. Champs : `id` interne, `ligne` (n° de ligne
  Excel, null pour les ajouts), `valeursClient` (A–K, O–AN d'origine), `saisies` (uniquement
  les champs modifiés/saisis par le terrain), `ajoute` (booléen), dates de modification.
  **Principe : les saisies terrain sont stockées séparément des valeurs client** — c'est ce
  qui permet les badges « corrigé », la fusion au réimport et l'export chirurgical.
- `photos` : Blob JPEG compressé, `branchementId`, index, date, nom de fichier calculé.
- `parametres` : préférences simples.

Statut d'une fiche (calculé, pour filtres et badges) :
- **À faire** : aucune saisie d'identification.
- **Identifié** : AG = 1 ou constat coffret (O) renseigné.
- **Reporté** : AH renseigné.
- **Point d'arrêt** : AK renseigné. **DI technique** : AL renseigné.
- **Ajouté** : créé dans l'app.

Complétude affichée sur la fiche : O, P, Q, S, T renseignés (+ U si T=DPBE, + R si Q=PE).

## 6. Import

1. L'utilisateur choisit le .xlsx (sélecteur de fichier ; sur Android, depuis Téléchargements/partage).
2. Vérifications : présence de l'onglet `Protection Branchements 2032` et du tableau `Tableau1`,
   en-têtes ligne 3 conformes aux 41 colonnes attendues. Sinon : message d'erreur explicite
   (« Ce fichier ne ressemble pas à une Annexe 7 PB 2032 : … ») et abandon sans rien modifier.
3. Extraction : lignes de données (une ligne est « donnée » si au moins une cellule A–K non vide),
   listes déroulantes, plages nommées, valeurs de référence pour V.
4. Stockage du Blob original + enregistrements branchements. Écran de synthèse : nb de
   branchements, communes, rues, déjà identifiés/reportés.
5. Si un dossier existe déjà : proposer **Remplacer** (repartir de zéro, confirmation explicite
   car les saisies locales sont perdues) ou **Mettre à jour** (fusion, §10).

## 7. Écrans

### 7.1 Accueil
Nom du dossier, avancement global (x/y identifiés, reportés), boutons : Rechercher (écran
principal), Importer / Mettre à jour, Exporter Excel, Exporter photos, Ajouter un branchement.

### 7.2 Recherche (écran principal terrain) — ordre validé par l'utilisateur
1. **Bouton SCAN** en premier, pleine largeur : caméra + lecture code-barres
   (API `BarcodeDetector`, hors ligne) → correspondance sur le matricule compteur (H)
   → ouverture directe de la fiche. Repli si API indisponible ou code illisible :
   saisie manuelle du matricule.
2. **Champ de recherche globale** : filtre instantané sur rue, n°, nom client, PCE,
   matricule (insensible aux accents/majuscules).
3. **Navigation hiérarchique** : Commune → Rue (badge « 12/27 identifiés ») → liste des
   branchements (n° trié intelligemment : 2, 4, 4B, 11 ; libellé = n° + complément + nom client
   + pictogramme d'état) → fiche.
4. **Filtres** : état (à faire / identifié / reporté / point d'arrêt / DI technique / ajouté)
   et phase terrain.

### 7.3 Fiche branchement
- **En-tête** : adresse, nom client, PCE, matricule, état technique, type client (A–K).
  Modifiable via « Corriger » ; un champ corrigé affiche un badge et la valeur client d'origine
  (« client : DUPOND »). Correction annulable (retour à la valeur client).
- **Section Identification** (O, P, Q, R en cascade, S, T, U conditionnel, AE, AF, AG) :
  listes déroulantes du fichier, **V affichée en direct** (« Pression : MPB (calculée) »).
- **Section Report** (AH, AI, AJ, AK, AL, AM, AN).
- **Photos** : vignettes, bouton « + Photo » (caméra ou galerie), suppression possible.
- Indicateur de complétude. Enregistrement automatique à chaque champ (pas de bouton
  « Enregistrer » à oublier).

### 7.4 Ajout d'un branchement
Formulaire : commune (choix parmi celles du dossier → INSEE déduit automatiquement, ou saisie
libre), rue (suggestions), n°, complément, nom, PCE, matricule, type client, puis fiche normale.
Si l'ajout est fait depuis une rue, commune et rue sont préremplies. Les fiches ajoutées portent
un badge « Ajouté » et sont incluses dans recherche, filtres, photos et exports.

## 8. Photos

- Capture caméra ou galerie ; plusieurs photos par branchement.
- **Compression à la capture** (canvas) : côté long ≤ 2 000 px, JPEG qualité 80 % →
  ~300–500 Ko/photo. Objectif : intérieur de coffret exploitable, n° de compteur lisible.
  Paramètres ajustables après validation sur photos réelles de l'utilisateur.
- **Nommage** : `{N°}_{RUE}_{PCE}_{i}.jpg` (n° en premier — décision utilisateur).
  Normalisation : majuscules, accents supprimés, espaces → `-`, caractères interdits retirés.
  Exemple : `4_RUE-DES-GENETS_GI02938475_1.jpg`. Cas particuliers : sans n° → `SN` ;
  sans PCE → identifiant de ligne (`L0937`) ; branchement ajouté sans PCE → `A0001`.
  Le nom est recalculé à l'export si l'adresse a été corrigée entre-temps.
- **Export** : ZIP des photos renommées (tout le dossier, ou filtré par phase/rue/commune),
  téléchargé puis déposé par l'utilisateur sur la plateforme dédiée.

## 9. Export Excel — exigence de fidélité absolue

Principe : **le fichier exporté est le fichier original, pas une regénération.**

1. Partir du Blob original stocké (ou du dernier fichier de mise à jour, §10).
2. Dans `xl/worksheets/sheet2.xml` (texte, par bloc `<row>`) : pour chaque branchement ayant
   des saisies, écrire les valeurs dans les cellules concernées uniquement (A–K corrigées,
   O–U, AE–AG, AH–AN). Les cellules texte sont écrites en « inline string » (pas de
   modification de `sharedStrings.xml`) ; AG/AM/AD et U en numérique. Le style (`s=`) de la
   cellule existante est conservé.
3. Branchements ajoutés : remplissage des premières lignes vides du tableau (935+), déjà
   formatées avec formules V/AB et validations (vérifié sur le fichier réel).
4. Ne jamais toucher : L–N, W–AD, AO, V (sauf exception §3.4), les autres onglets, les
   en-têtes, les styles, les validations.
5. Activer le recalcul à l'ouverture (`fullCalcOnLoad` dans `calcPr` de `workbook.xml`)
   pour que V et l'onglet RCT se mettent à jour chez le client.
6. Nom : `{nom original} - export {AAAA-MM-JJ}.xlsx`. Téléchargement (PC) ou partage (Android).

L'export ne modifie pas l'état local : il peut être refait à volonté.

**Critère d'acceptation** : le fichier exporté s'ouvre dans Excel sans réparation ; toutes
les listes déroulantes, couleurs, fusions, colonnes masquées et formules (V, AB, onglet RCT)
sont intactes ; seules les cellules saisies diffèrent ; les compteurs du RCT reflètent les
saisies après recalcul.

## 10. Mise à jour par un nouveau fichier client (réimport-fusion)

1. L'utilisateur importe la nouvelle version ; l'app rapproche les lignes :
   **clé primaire = PCE** ; à défaut (PCE vide) : INSEE + rue + n° + complément + nom.
2. Le nouveau fichier devient la base d'export. Les `saisies` terrain (et photos) sont
   réappliquées aux lignes correspondantes.
3. **Rapport de fusion** affiché : lignes nouvelles, lignes disparues (saisies orphelines
   conservées et signalées), conflits « le client a modifié une valeur que vous aviez
   corrigée » (la saisie terrain prime, le conflit est listé).
4. Les branchements ajoutés dans l'app sont conservés (sauf si le nouveau fichier contient
   désormais leur PCE : ils sont alors rapprochés de la ligne client).
5. Opération annulable tant qu'elle n'est pas confirmée (l'ancien état n'est remplacé
   qu'à la confirmation du rapport).

## 11. Gestion des erreurs

- Import : fichier illisible / mauvais onglet / en-têtes inattendues → message explicite, rien n'est modifié.
- Quota de stockage : contrôle avant enregistrement photo ; alerte au-delà de 80 % avec taille du dossier.
- Caméra ou `BarcodeDetector` indisponibles → replis (galerie / saisie manuelle).
- Écriture export : vérification interne post-injection (XML bien formé, nb de cellules modifiées = attendu) avant de proposer le téléchargement.
- Toute erreur inattendue : message en français + possibilité de copier le détail technique.

## 12. Tests (`node --test`)

- `regles` : formule V (tous les cas du §3.4, y compris valeurs vides), statuts, complétude, tri des numéros (2 < 4 < 4B < 11), normalisation des noms de photos (accents, doublons).
- `xlsx-reader` / `xlsx-writer` : sur une **fixture synthétique** reproduisant la structure exacte (tableau, listes, validations x14, formules V/AB, lignes vides) — import puis export sans saisie = fichier fonctionnellement identique ; export avec saisies = seules les cellules attendues changent ; ajout de ligne correct.
- `fusion` : correspondance PCE, repli adresse, nouvelles lignes, disparues, conflits.
- Vérification manuelle de bout en bout avec le vrai fichier du lot 5 (hors dépôt) avant première utilisation terrain, dont ouverture de l'export dans Excel.

## 13. Déploiement et mise à jour

Identique à l'app VPS : `git push` sur `main` → GitHub Pages ; incrément de la version de
cache du service worker à chaque livraison ; le téléphone propose « Recharger » au prochain
lancement connecté. Les données IndexedDB survivent aux mises à jour de l'app.
